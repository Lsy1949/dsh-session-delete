# dsh-session-delete

给 DeepSeek Harness（DSH）的会话与工作区加一个**垃圾桶**。

移入垃圾桶**不是删除**：记录整体搬出会话库，随时可以原样放回；只有「永久删除」和「清空垃圾桶」才真正销毁数据。项目目录、代码、文档永远不被读写。

适用 DSH `>= 0.2.1-rc.2 < 0.3.0`。2.x 是新实现，不读取 1.x 的旧垃圾桶条目。

## 功能一览

| 位置 | 动作 | 结果 |
|---|---|---|
| 会话行「⋯」菜单 | **移至垃圾桶…** | 该会话的日志目录搬进垃圾桶，侧栏不再列出；可恢复 |
| 会话行悬停按钮 | **垃圾桶图标** | 同一动作，点击直接弹出确认框 |
| 侧栏全局面板列表 | **垃圾桶**图标 | 打开垃圾桶面板 |
| 垃圾桶面板 | 每条 **恢复** | 搬回原路径，并尽量挂回原工作区（工作区连同原会话顺序还原） |
| 垃圾桶面板 | 每条 **永久删除** | 只删这一条，确认框二次确认 |
| 垃圾桶面板 | 勾选后 **恢复所选** | 一次把勾中的几条全部放回，不用逐个点 |
| 垃圾桶面板 | 勾选后 **删除所选** | 只删勾中的几条，其余不受影响 |
| 垃圾桶面板 | **全选 / 取消全选**、每组的 **本组全选** | 大批量操作不用点很多次 |
| 垃圾桶面板 | **扫描会话目录** | 找出磁盘上还在、但应用里已经没有的会话目录（反过来也能查） |
| 垃圾桶面板 | **清空垃圾桶** | 确认后一次删光 |
| 会话行（日志已不在磁盘） | **从列表中移除** | 会话库还登记着、但日志目录已经不存在的「幽灵行」，归档掉即可从侧栏消失 |
| 垃圾桶面板 → 工作区 | **删除工作区…** | 整个工作区（全部会话 + 工作区登记）作为一个条目进垃圾桶，可整体恢复 |
| 设置 → **垃圾桶** | 目录、迁移、占用、操作日志 | 换目录时默认把现有条目一并迁走；日志可打开文件 / 复制路径 / 清除 |

所有破坏性动作走同一个确认框；所有失败都会说清原因（`missing` / `live` / `ambiguous` / `exists` / `unavailable` …）。

## 安装

```bash
dsh plugin --profile desktop add https://github.com/Lsy1949/dsh-session-delete.git
```

`desktop` 换成你的 profile 名（桌面端默认 `desktop`）。

本地目录（离线或自己改代码时）：

```bash
git clone https://github.com/Lsy1949/dsh-session-delete.git
dsh plugin --profile desktop add "D:\path\to\dsh-session-delete"
```

装完**必须完全退出并重启 DSH**（托盘图标右键退出，不是关窗口）——插件的宿主半只在进程启动时加载。

升级：`git pull`（或重新 `add`）后同样完全重启。

### 版本与 DSH 兼容

| 插件版本 | DSH 范围 | 获取方式 |
|---|---|---|
| `main`（默认） | 以当前 `engines.dsh` 声明为准（现为 `>= 0.2.1-rc.2 < 0.3.0`） | 上面的安装命令 |
| 更新 DSH 的适配 | 以 Release 说明为准 | 完成后落在 `main` |
| 旧 DSH 的维护线 | 只收 bug 修复，范围冻结 | 对应维护分支（如 `dsh-0.2`），在 `main` 前进到新 DSH 时切出 |

每个发布都会打 tag，GitHub Release 说明会注明适配的 DSH 范围。当插件宣布
适配更新的 DSH 后，仍在用旧 DSH 的用户请固定到对应维护分支：

```bash
git clone -b dsh-0.2 https://github.com/Lsy1949/dsh-session-delete.git
dsh plugin --profile desktop add "D:\path\to\dsh-session-delete"
```

插件自更新时也会对照 `engines.dsh`：远端的兼容范围变了就不自动拉取，
报告 `engines-changed`，不会悄悄把你带进不兼容的版本线。

手工兜底（`dsh plugin` 不可用时）：

1. 把包放到 `~/.dsh/profiles/desktop/node_modules/dsh-session-delete`
2. 在 `~/.dsh/profiles/desktop/cordis.patch.yml` 末尾追加：

```yaml
- insert:
    - id: dsh-session-delete
      name: dsh-session-delete
```

3. 完全重启 DSH

## 日常使用

**把会话放进垃圾桶**：会话行「⋯」→ 移至垃圾桶…，或直接点悬停的垃圾桶图标 → 确认。会话从侧栏消失，进入垃圾桶。

**把整个工作区放进垃圾桶**：垃圾桶面板 → 工作区 → 删除工作区…，确认后该工作区所有会话作为一个条目进垃圾桶，工作区登记一并移除。

**找回记录**：打开垃圾桶面板 → 每条右边的「恢复」。工作区条目恢复时会把会话按原顺序放回。

**只删几条**：勾选记录 → 删除所选；或直接点那一行的「永久删除」。

**彻底清理**：清空垃圾桶（确认后不可撤销）。

## 设置

设置 → 垃圾桶：

| 项 | 说明 |
|---|---|
| 垃圾桶目录 | **一个输入框**：直接输入或粘贴路径，或点框右侧的 **浏览…** 在系统的文件夹对话框里选（桌面端是应用自己的原生对话框）。必须是绝对路径，支持 `~`；留空表示用默认目录 `<DSH home>/trash/sessions` |
| 修改目录时一并迁移 | 默认勾选；迁移失败会整体回滚，不会搬一半 |
| 当前 / 默认目录 | 直接显示，方便核对 |
| 操作日志 | 查看 / 打开日志文件 / 复制路径 / 清除 |
| 打开垃圾桶目录 | 交给系统文件管理器定位 |

挂载行也支持配置（优先级低于设置页保存的值）：

```yaml
- id: dsh-session-delete
  name: dsh-session-delete
  config:
    trashDir: 'D:\dsh-trash'   # 绝对路径，支持 ~
```

**约束**：垃圾桶目录不能与会话库重叠（相等、包含、被包含都拒绝）。否则「移入垃圾桶」等于把文件搬回会话库，「清空」还可能删到活数据。

## 垃圾桶面板

面板按**工作区分组**，和侧栏的结构一致，一眼就能看出哪条记录属于哪个工作区：

```
▾ 项目A                                   3 条 · 5.2 MB    ☐ 本组全选   [收起]
    ☐ 论文截图                            11/11 23:29 · 2.1 MB   [恢复][永久删除]
      C:\work\a\论文
    ☐ 实验数据                            11/11 22:10 · 3.1 MB   [恢复][永久删除]
▾ 整个工作区（已删除的）                    1 条 · 88 MB                       
▾ 未分组                                   1 条 · 100 B
```

- 组标题就是工作区名（没有名字时退回工作区目录名），悬停显示它指向的文件夹
- 组头有该组的**条数与总占用**，还有 **本组全选** 与 **收起/展开**
- 不在任何工作区的会话进「未分组」，和侧栏用同一个词
- 被整组删掉的工作区条目也在它自己的组里，条数就是它带的会话数
- 勾选后同时出现 **恢复所选** 与 **删除所选**：安全的方向和危险的方向并排，少点几次才是真的少出错
- 体积在移入时算好写进 manifest，面板刷新不再遍历整个垃圾桶（只有旧条目才现算）

### 扫描会话目录

会话被删掉之后，日志目录有时会留在于磁盘上——应用里看不到，却一直占着空间。面板里的 **扫描会话目录** 会把它们找出来：

```
▾ 扫描会话目录        磁盘上有 12 个会话目录，其中 3 个已不在列表中        [移入所选（2）] [开始扫描]
    ☐ 论文截图      2.1 MB · 11/10 16:00 · C-Users-Test-project   [打开目录] [移入垃圾桶]
    ☐ （没有名字的会话） 100 B · 11/09 09:12 · C-Users-Test-project  [打开目录] [移入垃圾桶]
```

- **只看得出"应用里没有"**：判定依据是会话库的 `list()` 与各工作区的 `sessionIds`，两者都不认的目录才算孤立
- 名字仍然从日志里的 `session/title` 事件恢复，恢复不出就叫「没有名字的会话」，不会拿 `session-e4b8a47f…` 当标题
- **移入垃圾桶 = 整条目录搬进垃圾桶**，不是删除：在下面的列表里随时能 **恢复**，放回原来的 `sessions/<组>/<id>`
- 已经在垃圾桶里的会话不会重复出现在扫描结果里
- 应用**刚刚又把它列出来**的目录会被拒绝（`still-listed`）；正在跑的会话也会被拒绝（`live`）
- 空目录、跨卷搬移、被占用的目录都有对应的失败原因，失败的会如实报出来，不会假装成功
- 体积只在**要显示的 200 条**上计算，几千个遗留目录也不会让一次点击变成一分钟

### 目录是怎么选的

浏览器半打不开原生对话框（插件拿不到应用窗口），所以由宿主去开，按顺序尝试三种：

1. **Electron 的 `dialog.showOpenDialog`**——桌面端就是它，模态、挂在应用窗口上、记得上次的位置
2. 平台自带的文件夹对话框——Windows 用 PowerShell 的 `FolderBrowserDialog`，macOS 用 `osascript choose folder`，Linux 用 `zenity --directory`（宿主跑在纯 `node` 下时走这条）
3. 都没有就返回 `unsupported`，界面自动切到「手动输入路径」

输入框和浏览按钮是**同一个字段**：框里永远可以打字，按钮只是把对话框选到的路径填进去（和 VS Code、Windows 设置里那种写法一致）。对话框 180 秒无响应算超时；取消不算错误（只提示「没有选择文件夹」）；`DSH_SESSION_DELETE_NO_PICKER=1` 可整体关掉（测试与无头部署用）。改了内容不会立刻生效——点「保存」才写入，迁移勾选也在那时起作用，旁边会提示「有未保存的改动」。

## 更新

设置 → 垃圾桶 → **更新**：显示当前版本与仓库里的最新版本，可以手动「检查更新」「立即更新」，也可以打开两个开关：

| 开关 | 默认 | 作用 |
|---|---|---|
| 自动检查更新 | 开 | 启动约 10 秒后在后台问一次仓库；不下载任何东西 |
| 自动拉取更新 | 关 | 发现有新版本时后台拉取并校验；失败自动回滚 |

**更新只替换磁盘上的文件，当前进程仍跑旧代码——完全重启 DSH 后才生效。** 面板会一直提示这一点。

### 面向所有安装方式

检查更新**不需要** git：先直接读仓库里的 package.json（HTTPS，无需凭据，通常 2 秒内），读不到才回退到 git fetch。所以：

| 安装方式 | 能检查 | 能自动更新 | 界面怎么提示 |
|---|---|---|---|
| 用 git 地址安装（有 .git） | 是 | 是（git pull） | 出现「立即更新」 |
| 复制/解压安装（没有 .git） | 是 | 是（下载压缩包） | 出现「立即更新」 |
| 没有 git 命令 | 是 | 是（下载压缩包） | 出现「立即更新」，并注明走 HTTPS |
| 断网 / 连不上 GitHub | — | — | 「检查超时」或「连不上 GitHub」，并给出手动命令 |

**更新不需要 git**：检出（且 git 可用）走 `git pull --ff-only`；其余情况直接把 GitHub 的 `tar.gz` 下载下来解压——只要求 HTTPS。

检出但 `git pull` 因网络失败（代理只放行 HTTPS、git 传输被封等）时，会**自动改走压缩包**那条路，因此"git 不通"不再等于"更新不了"。启动时的那次自动检查失败（断网、超时）会**静默重试两次**（60 秒、180 秒后）。

版本元数据会依次尝试 `raw.githubusercontent.com` → `github.com/<repo>/raw/…` → `api.github.com`，压缩包会依次尝试 `codeload.github.com` → `github.com/<repo>/archive/…`：某个域名被墙或不通不会让整次检查失败（只封 raw 的网络很常见）。两条路都做同样的事：先**校验**、再**备份**当前目录、覆盖写入、写入后**再校验**，任何一步失败就回滚。

面板底部**始终**显示仓库地址和手动更新命令，任何环境都有出路：

    dsh plugin --profile <profile> add https://github.com/Lsy1949/dsh-session-delete

检查有硬截止：单次请求 8 秒、git fetch 10 秒、整次检查 15 秒上限。超时就明确说「检查超时」，**不会一直卡在「检查中」**。

**是不是 git 检出，由 `.git` 目录决定，不看 git 命令能不能跑**——这是两个不同的问题，修法也不同：

- 找不到 git 命令时（从启动器打开的桌面应用可能没有终端的 PATH），会依次找 `git`、`D:\Git\cmd\git.exe`、`C:\Program Files\Git\cmd\git.exe`、`%LOCALAPPDATA%\Programs\Git\cmd\git.exe`（macOS/Linux 找 `/usr/bin/git` 等），也可以用 `DSH_SESSION_DELETE_GIT` 直接指定
- 都找不到就报 `no-git-binary`，**不会再误报「这个安装不是 git 检出」**
- 断网时回答里仍然带着「你是哪种安装、能不能自动更新」，界面说的永远是真正的问题

> 注意：Node 的 fetch 不读系统代理，只有 git 会读 HTTPS_PROXY。靠代理出网、且安装是 git 检出的机器，检查与更新都正常；复制安装的只能手动更新。

### 为什么不会把应用弄坏

自己更新自己是最容易出事的功能，所以每一步都有护栏：

- **不是 git 检出就不动**（`not-git`）：只支持在干净的检出里 `pull`
- **连不上 GitHub 就说连不上**（`offline`）：不会把网络问题伪装成「已是最新」
- **走本地代理时**：`git fetch` 会读 `HTTPS_PROXY` 环境变量，但系统的 WinINET 代理设置它读不到；
  若你的机器依赖本地代理（例如 `HTTPS_PROXY=http://127.0.0.1:7897`），需要在启动 DSH 的环境里设置好，
  否则检查会如实报 `offline`
- **工作区有未提交改动就拒绝**（`dirty`）：绝不覆盖你的改动，也因此回滚永远安全
- **DSH 兼容范围变了就拒绝**（`engines-changed`）：远端的 `engines.dsh` 和已装版本不一致时，
  说明那是另一条兼容线，换分支是有意为之的操作，绝不自动发生
- **只做 `git pull --ff-only`**：不合并、不 rebase，冲突不会被自动解决成半成品
- **拉完先校验**：`package.json` 的名字 / `manifestVersion` / 入口字段必须仍然正确，`index.js`、`client.js`、`lib/host/*.js` 逐个过 `node --check`，`client.js` 必须仍然向 Module Loader 注册
- **校验失败自动回滚**（`rolled-back`）：`git reset --hard` 回到拉取前的提交，并把原因写进结果
- **`pull` 失败也回滚**（`pull-failed`）：分支已分叉时同样复位
- **同一时间只允许一个更新**（`busy`）；每个子进程与网络请求都有超时（git 60 秒，网络 15 秒）
- **绝不重启应用**：不会打断你正在跑的会话，重启与否由你决定
- **可以彻底关掉**：`DSH_SESSION_DELETE_NO_UPDATE=1` 让检查与更新都直接返回 `disabled`（测试与无头部署用）

更新会记进操作日志（`update.apply` / `update.apply.failed`，带 from/to、改动文件数、失败原因）。

## 名字与路径从哪来

每条记录显示的是**你在侧栏看到的名字**，名字有三个来源，按顺序取：

1. 移入时从界面上记下来的（最准）；
2. 没记下来（通过接口移入，或旧版本移入）时，去读条目里那份日志——DSH 把每次接受的标题写成 `session/title` 事件存进日志，取最新一条，不需要标题服务也不需要模型调用；
3. 日志里也没有，才退回所在文件夹名并附一个短 id（如 `#e4b8a47e`）。

名字下面一行是**它来自哪个文件夹**（长路径省略显示，悬停看全）；再下一行是原工作区、移入时间和占用大小；悬停还能看到完整会话 id。

## 会话目录是怎么找到的

DSH 的 `sessionPersistence.list()` / `stat()` 只给会话的 header、版本和大小，**不给日志文件路径**（这一版里 `location` 只出现在错误对象上）。所以插件不推断目录名，而是**读**会话库：在 `<DSH home>/sessions/` 下看一级分组目录，找名字正好等于会话 id 的那一个。

分组目录名是 DSH 内部编码（例如 `--C-Users-Administrator-Desktop-1-~65B0~5EFA~6587~4EF6-5939--`），插件从不算它，所以 DSH 换编码规则也搬不错地方。

| 情况 | 结果 |
|---|---|
| 找不到 | `missing`（404），什么都不动 |
| 同一 id 命中两个目录 | `ambiguous`（409），拒绝而不是猜 |
| 形状不是 `sessions/<组>/<会话>` | `bad-path`，拒绝 |

## 安全边界

- **只在真有回合在跑时拒绝**（`live`）——侧栏已经加载但空闲的会话照样可以移入；
  判定不了就当空闲处理，真被占用时由移动本身报 `busy`（Windows 上打开的文件句柄就是这个码），
  绝不会退化成"拷贝一份正在写的日志"
- **只搬** `sessions/<组>/<会话>` 形状的目录；manifest 里的路径不合规直接拒绝
- **恢复不覆盖**：目标已存在时返回 `exists`，绝不合并两份记录
- **删除只发生在垃圾桶内**；越界的 manifest 条目会被跳过
- **搬家失败会回滚**：文件回原位、归档标记复原，不会留下半个条目
- 所有写操作是**同源 POST + JSON**：`Origin` 与 `Host` 不一致直接 403，非 POST 405
- 「交给文件管理器」只能指名 `log` / `config` / `trash` 三个目标，**调用方不能传任意路径**
- 为了让行立刻消失，移入前会调用官方归档接口；恢复时只撤销**我们自己打的那个**归档标记，你原本归档的状态保持不动

### 幽灵行（日志目录已经不在了）

有些行 DSH 还列着，但磁盘上已经没有它的日志目录了。来源有两种：你手工删过 `~/.dsh/sessions/**/session-…`；或者**被早先版本的「清空垃圾桶」制造出来**——那个版本在永久删除后顺手撤销了归档标记，于是数据没了、行却回到侧栏，点开就报 `ENOENT: no such file or directory … session.v4.jsonl.zstd`。

**清空/永久删除现在不再撤销归档标记**（标记正是让行消失的东西），所以不会再产生新的幽灵行。已经存在的：

- 垃圾桶面板顶部会列出它们：「有 N 个会话还列在侧栏，但它的日志文件已经不在磁盘上」+ **归档这些空行** 按钮
- 单条也可以：会话行「移至垃圾桶」如实报 `missing`，确认框随即提供 **从列表中移除**
- 两者都只调用官方归档接口，**不做任何文件操作**，之后仍能在 DSH 的「已归档」里找回
- 决定会写进操作日志（`session.retire`，带 `reason: "no-directory"`）

## 已知限制

- **工作区行没有可扩展的菜单槽位**。DSH 只开放 `sidebar.workspaces.session.menu.item`（会话行）这类槽位，所以整组操作放在垃圾桶面板里，而不是伪造菜单
- **会话必须有「每会话一份产物」的存储后端**（官方 JSONL 后端满足）。换成不落单文件的后端时，插件对会话不可见
- **依赖磁盘布局**：`sessions/<组>/<会话>` 是唯一接受的形状；DSH 若改布局，插件会拒绝而不是乱搬
- **没有全局 toast 服务**：会话行操作失败时错误显示在确认框里，垃圾桶面板里才是完整状态
- 卸载后，垃圾桶目录里未删除的记录仍在原处，插件不再管理它们

## 排障

浏览器半每次启动都会把自己的状态报给宿主：

```bash
curl -s -X POST -H "content-type: application/json" -d "{}" http://127.0.0.1:<端口>/dsh-session-delete/state
```

响应里的 `client` 字段：

| 字段 | 含义 |
|---|---|
| `phase` | `factory` / `client.applied` / `client.failed` / `client.settled` |
| `registered` | 注册过的槽位 |
| `entries` | 每个槽位**真正**持有的条目数 |
| `failures` | 失败与渲染崩溃原因 |
| `patched` | 工作区文案改名是否生效 |

界面崩溃不会留空白：面板和设置页都包了错误边界，会显示「渲染失败：<原因>」并写进上面这份报告。

### 操作日志里记了什么

日志文件（`<DSH home>/dsh-session-delete/operations.log`，JSONL）里有两类行，一行一个 JSON：

| 类型 | `kind` | 内容 |
|---|---|---|
| 发生了什么 | 无 | 动作、对象名字、条数、原因码 |
| 谁在什么时候怎么调的 | `request` | 路由、HTTP 状态、耗时、参数、返回摘要、报错堆栈 |

两类行共用这些字段，排查时一行就能自证：

```json
{"at":"2026-11-12T00:32:42.364Z","atMs":1794414762364,
 "actor":{"osUser":"Administrator","host":"Computer-L","platform":"win32","release":"10.0.26200","pid":35824},
 "reqId":"req-mwcc7vy0-t0clwg",
 "request":{"route":"/dsh-session-delete/session/move","method":"POST","origin":"http://127.0.0.1:58434",
            "userAgent":"Mozilla/5.0 …","remote":"127.0.0.1"},
 "kind":"request","op":"request.session.move","ok":true,"status":200,"durationMs":42,
 "args":{"sessionId":"session-...","title":"软件工程实训第二阶段报告撰写"},
 "result":{"trashId":"20261112-003242-001-session-...","cwd":"C:\\Users\\..."}}
```

- `at` / `atMs`：ISO 时间与毫秒时间戳；`actor`：系统用户名、主机名、平台、内核版本、进程号
- `reqId`：同一次请求产生的所有行共用一个 id，跨行串起来看
- `args` / `result`：请求参数与返回摘要（数组只留长度，长字符串截断）
- 失败时多一个 `error: { message, stack }`，堆栈也进日志
- 每次请求都记；只有 `client/report` 和 `log/read` 这种自检轮询不记，免得淹没关键信息

面板（设置 → 垃圾桶 → 查看操作日志）只列"发生了什么"那一类，每条一句人话，时间本地化、动作用名字；
请求明细不进面板，面板底部会写「另有 N 条请求明细」，要看就点「打开日志文件」：

```
11/11 23:29   移入垃圾桶「仓颉编译器实验截图」
11/11 23:46   永久删除「论文截图」
11/11 23:50   垃圾桶目录改为 D:\dsh-trash（迁移 2 条）
```

```

完整细节（会话 id、原始目录、条数、用户、耗时、报错堆栈）都在日志文件里，面板给了「打开日志文件」和「复制路径」。
日志超过 1 MB 会轮转成 `operations.log.1`，只保留最近一份。

## 数据放在哪

| 内容 | 位置 |
|---|---|
| 垃圾桶条目 | `<trashDir>/items/<trashId>/manifest.json`；会话在 `session/`，工作区在 `sessions/<id>/` |
| 插件设置 | `<DSH home>/dsh-session-delete/config.json` |
| 操作日志 | `<DSH home>/dsh-session-delete/operations.log`（JSONL，超过 1 MB 轮转一份 `.1`） |

## 卸载

```bash
dsh plugin --profile desktop remove dsh-session-delete
```

然后完全重启。可选清理：删掉 `<DSH home>/dsh-session-delete/`（设置与日志）和垃圾桶目录——**垃圾桶里还没删的记录会被真正删除**。
